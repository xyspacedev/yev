# Plan 5: yev-4b Stage 1 (targeted data, retrain, evaluate) — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the Stage 1 data families, retrain yev-4b with up to 10 options and 12,288-token rows, run the position-bias check, and evaluate it against the publish gate.

**Architecture:** The code is laid out as follows:

- **Programmatic families** are new modules in `src/yev/generators/`, registered in the existing `RULE_GENERATORS` (the `yev gen-rules` CLI).
- **The Opus long-document family** extends `src/yev/generators/llm/` with a document mode: a writer produces a document plus questions, then a blind check runs on each question.
- **The public slice** is a new source in `src/yev/sources/`.
- **The contamination filter** gains a multi-benchmark fingerprint set.
- **Recipes and training** get a Stage 1 recipe and config. The schema, data and trainer limits are raised to 10 options and 12,288 tokens.
- **Evaluation** gains a shuffled-options mode and a `yev gate` report.
- **Running it** is a controller runbook on the AWS box.

**Tech Stack:** Python ≥ 3.11, uv, torch, transformers 5.x, peft, pytest. Opus writer and checker subagents run through the existing `yev synth` file protocol.

**Spec:** `docs/superpowers/specs/2026-10-02-yev-4b-stage1-design.md` amends `docs/superpowers/specs/2026-09-29-yev-4b-system-one-design.md`.

## Global Constraints

- **Never train on any reported benchmark:** DecideBench test, WorkflowEvals (all four `typesafe/evalsafe-*`), JevBench public, DynaBench test, R-Judge, and the Decision Index 0.2.1 test sets.
- **Opus writers never see benchmark material.** Scenarios come from `yev.generators.llm.families.DOMAINS` and the new document topic list.
- **DecideBench test is scored exactly once on the Stage 1 model,** after it is final, and is never used to choose between models. The existing per-variant sentinel must be lifted deliberately for this one run. It is lifted for Stage 1 by the `--stage stage1` sentinel name, never by deleting the Stage 0 sentinel.
- **Options:** choice questions take 2–10 options (letters A–J), and score questions 3–11 levels in scale order. Stage 0 rows with 6 options or fewer must train and evaluate bit-identically when `n_max` = 6.
- **Lengths:** the maximum training length is 12,288 tokens. Rows longer than that are dropped and counted, never truncated.
- **Recipe:** a fresh LoRA from `Qwen/Qwen3.5-4B-Base` with r = 64, α = 128, all linear layers, learning rate 1e-4, cosine schedule, 3% warmup, 1 epoch, the `lc100` losses, and no pair or permutation loss.
- **No uploads anywhere.** The box's host, key and instance id never enter the repo. Scripts read `YEV_TRAIN_HOST` and `YEV_TRAIN_KEY`.
- **GPU:** whatever instance `YEV_TRAIN_HOST` points at, an L40S (g6e.xlarge) or a single H100 if the quota is approved. Nothing in the code may assume one or the other.

## Rulings (deviations from the spec)

1. **Decision Index contamination is enforced by name plus targeted fingerprints, not full fingerprints of all 38 test sets.** Building the whole suite is about 7 GB and needs gated terms. Instead:
   - the public slice may only use datasets absent from the Decision Index's source list, which is checked by name in a test;
   - fingerprints are built for every Decision Index benchmark whose source dataset is already in our pool (BANKING77, CLINC150, ARC, GSM8K, FinEntity via eikos);
   - generated rows are fingerprinted against the other reported benchmarks.

   Cost if wrong: a Decision Index item paraphrased by Opus slips through. The risk is low, because writers never see benchmark text.
2. **Family 6 documents skip edit attribution** (main spec §4.3 step 4). Documents are multi-question, not contrastive pairs, so there is no flipping edit to attribute. The blind check and soft labels still apply.
3. **Family 7 padding labels are unchanged from the source row,** and each padded row's distractor text is drawn from our own generated documents (families 3 and 6), never from public text. Its licence is the source row's licence.

## Review Focus

1. **A 7–10-option row must keep its letters, targets and readout aligned.** A target vector padded to `n_max`, or a letter slice, must never truncate options 7–10. Test: `test_ten_option_row_targets_and_letters_aligned` (Task 1).
2. **Stage 0 bit-identity:** with `n_max` = 6, encode, batching and readout outputs are unchanged. Test: `test_n_max_six_bit_identical_to_stage0` (Task 1).
3. **Date arithmetic across month, year and leap boundaries must be computed, not formatted.** Test: `test_elapsed_days_across_feb29_and_year_end` (Task 3).
4. **Questions sharing one long document must never be split between train and dev/calibration.** Test: `test_document_questions_share_split` (Task 9).
5. **The extended contamination filter must drop a row containing any reported benchmark's 8-gram.** Test: `test_drops_rows_overlapping_any_benchmark` (Task 2).

### Task 10: Position-bias check and publish-gate report

**Files:**
- Create: `src/yev/gate.py`
- Modify: `src/yev/cli.py` (`yev eval --shuffle-options K --min-options 7`, and `yev gate`)
- Test: `tests/test_gate.py`, `tests/train/test_shuffle_eval.py`

**Interfaces:**
- **`yev eval --shuffle-options K`** re-asks each dev row that has at least `--min-options` options under K seeded option permutations. Labels stay attached to their keys. It writes `position_bias.json` with:
  - `argmax_agreement` (the share of rows whose chosen key is the same in every permutation);
  - `mean_tv_distance` between the per-key distributions;
  - `by_n_options`.
- **`yev bench score --stage NAME`:** the DecideBench once-guard sentinel becomes `.scored-<stage>-<variant>` when `--stage` is given. Without it, the existing Stage 0 sentinel name and behaviour are unchanged.
- **`yev gate`** takes `--stage0-dev`, `--stage1-dev`, `--workflowevals DIR`, `--bench DIR`, `--decidebench DIR` and `--out gate.json`. It applies the spec §2 thresholds exactly:

  | Check | Minimum | Target |
  |---|---|---|
  | WorkflowEvals overall | 54.5 | 60 |
  | DecideBench test, with examples | 94.0 | 95 |
  | JevBench | 77 | |
  | DynaBench F1 | 54 | |
  | R-Judge F1 | 49 | |
  | Stage 0 dev accuracy | 93.0 | |
  | ECE | 0.05 | 0.04 |

  It prints PASS, TARGET or FAIL per row and an overall PUBLISHABLE yes/no, and computes the WorkflowEvals overall score as the equal mean of the four workflows' consensus headline metrics (invoice: `exact_actions`).

**Steps:**
- [ ] **Step 1: Write failing tests.**
  - `test_shuffle_keeps_labels_with_keys`.
